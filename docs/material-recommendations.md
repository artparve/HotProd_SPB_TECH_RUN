# Подбор материалов и локальный RAG

Реализован ограниченный baseline для существующих работ Java-калькулятора. Опубликованный каталог и правила остаются источником товаров и расчётных профилей. Отдельная база знаний содержит вручную проверенные утверждения и фрагменты источников, привязанные к точной версии товара. Подбор не утверждает полноту строительной технологии.

## Запрос и объяснение Ollama

`POST /api/v1/material-recommendations` принимает `works`, известные `conditions`, необязательный `query`, `designPreferences` и `explain`. Для поиска размеры не обязательны. Для последующего расчёта нужно передать полный `room`, `object` и `renovation`; исходные параметры сохраняются сервером на один час. UI доступен на странице расчёта в разделе «Подбор с источниками и ИИ-объяснением» и рассчитывает одну текущую комнату.

```json
{
  "works": ["paint"],
  "conditions": {"humidity": "normal", "load": "normal", "heated": true},
  "query": "белая краска",
  "explain": true
}
```

Неизвестные условия передаются как `null` или отсутствуют; сервер возвращает вопросы. В опубликованных требованиях каждой категории задаются обязательные условия. Базовые влажность, нагрузка и отопление обязательны всегда. Дополнительные условия: `substrate`, `waterContact`, `floorHeating`, `covering`, `baseState`. Текстовые значения пока сопоставляются точно, без модельной нормализации и догадок.

При наличии актуальной базы знаний Java проверяет утверждения и формирует `pass` / `fail` / `unknown`. Отрицательное булево утверждение исключает товар; конфликт или отсутствие необходимого доказательства блокирует подтверждение. Источники разных SKU не подменяют друг друга. `fail` в ответ кандидатов не попадает. `unknown` отображается отдельно и не допускается к применению.

Поиск выполняется локально формулой BM25 (`k1=1.2`, `b=0.75`, версия `bm25-v1`) по названию и опубликованным фрагментам. Нормализация — нижний регистр Unicode и `ё→е`; токены — буквы и цифры. При равенстве используется стабильный UUID. Подтверждённые кандидаты ранжируются отдельно и показываются перед неподтверждёнными. Черновые тексты, дизайн и модель не снимают ограничения. Синонимы, dense retrieval, hybrid/RRF и реранкер ещё не включены: для них нужны отдельная оценка на русском наборе и измерения оборудования.

С `explain=true` и подтверждёнными кандидатами Java вызывает существующий аутентифицированный LLM-шлюз: `materials/explain` → `${OLLAMA_URL}/api/chat`, модель `${OLLAMA_MODEL}`. Используются существующие `LLM_SERVICE_URL` и `INTERNAL_SERVICE_TOKEN`; секреты не передаются браузеру. Общий semaphore шлюза ограничивает параллелизм всех операций. Запуск приложения не загружает модель. Для этой операции таймаут обращения к Ollama ограничен 30 секундами, ожидание Java — 35 секундами или меньшим общим лимитом `LLM_REQUEST_TIMEOUT_SECONDS`.

Модели передаются только ID, названия и фрагменты максимум десяти подтверждённых товаров, до десяти фрагментов каждого. Запрос и документы остаются данными пользовательского сообщения, инструкции задаются отдельным system-сообщением. Шлюз и Java проверяют схему, принадлежность товаров и ID фрагментов конкретному товару. Принятый текст имеет статус `unverified_model_text`: эти проверки не подтверждают смысловую достоверность ответа и не гарантируют устойчивости к любому prompt injection. UI выводит обычный текст без HTML и показывает структурированные источники отдельно. При выключенной/недоступной модели, занятости, таймауте или недопустимом ответе возвращается `deterministic` с причиной fallback.

## Публикация знаний

В административной панели доступен раздел «База знаний для подбора материалов». Оператор проверяет технические факты, контекст, актуальность, соответствие SKU и права на использование, затем вставляет пакет JSON и явно подтверждает публикацию. Программный доступ использует действующие admin-сессию и CSRF:

- `POST /api/v1/admin/knowledge-releases` — проверить и сохранить полную новую версию, активировать её;
- `POST /api/v1/admin/knowledge-releases/{id}/activate` — повторно проверить и активировать сохранённую версию для отката;
- `POST /api/v1/admin/knowledge-releases/{id}/revoke` — отозвать версию без возможности повторной активации.

Формат пакета закреплён в `docs/openapi.yaml`, Java `KnowledgeBundle` и frontend Zod `knowledgeBundleSchema`:

- `catalogReleaseId`, `ruleSetId` должны совпадать с текущей согласованной парой;
- `sources`: ID, название, издатель, HTTPS-ссылка, версия, даты получения/окончания актуальности, SHA-256; статусы только `rightsStatus=approved`, `reviewStatus=confirmed`;
- `chunks`: ID фрагмента, точный `productId`, `productVersionId=<catalogReleaseId>:<productId>`, `sourceId`, раздел и краткий текст;
- `claims`: свойство, значение, статус `confirmed|unknown|conflict`, ID подтверждающих фрагментов того же товара. Поддержанные свойства: `work`, `wet`, `highLoad`, `unheated`, `substrate`, `waterContact`, `floorHeating`, `covering`, `baseState`;
- `requirements`: существующая работа/категория из Java kits и обязательные условия. Отсутствие требования категории не даёт подтверждённой рекомендации;
- `combinations`: точная пара UUID товаров, статус `pass|fail|unknown` и фрагменты обоих товаров. В первом безопасном варианте применение нескольких товаров требует явного подтверждения всех пар выбранного комплекта.

SHA-256 документа и статусы проверки указывает оператор после фактической проверки: приложение не скачивает документы и не подтверждает права автоматически. Коллекции `data/rag/seed-v1` и `data/rag/documents-v1` не импортируются и не утверждаются автоматически. По похожему названию SKU не связываются.

Хранение: `knowledge_release` — полный неизменяемый корпус с checksum и manifest; `knowledge_pointer` — атомарно заменяемый указатель; `knowledge_revocation` — отзывы. Предыдущие версии сохраняются. Для BM25 manifest явно указывает отсутствие embedding-модели, размерность 0, версии нормализации и чанкинга, количество документов и товаров. Поиск строится из одного проверенного снимка на запрос, поэтому отдельного рассинхронизированного векторного индекса пока нет. При несовпадении версий/manifest/checksum, просроченном или отозванном источнике весь выпуск не подтверждает новое решение; используется поиск кандидатов без подтверждения совместимости.

## Применение к расчёту

`POST /api/v1/material-recommendations/{requestId}/estimate` принимает `project` с одной комнатой и явные `selections` в текущем формате `<roomId>:<kind> → productId`. Клиентские статусы совместимости не принимаются. Сервер загружает сохранённый контекст, сверяет комнату, тип объекта/ремонта и условия, фиксирует согласованную пару, перепроверяет версии знаний, товары, расчётную готовность и связки. Тот же снимок передаётся Java-калькулятору. Ни одна автоматически подобранная калькулятором строка не возвращается как явно выбранная: отсутствие выбора приводит к 422. Версионный конфликт или изменение комнаты — 409 `stale_recommendation`. Подбор без геометрии остаётся поиском; перед применением нужен новый подбор с `room` и контекстом проекта.

Существующие `/recommendations` и `/estimate` сохраняют поведение. Все используемые ими цены и нормы остаются учебными; подтверждение технического свойства не делает цену рыночной и не гарантирует бюджет. При недостающем расчётном профиле или упаковке кандидат не допускается к этому пути расчёта. Java по-прежнему проверяет остальные числовые параметры. Итог хранит снимок строк текущего формата и предупреждение с ID подбора/базы знаний; отдельного неизменяемого архивного хранилища смет эта функция не добавляет.

## Наблюдаемость и границы приёмки

Micrometer: `repaircalc.material.verification`, `.retrieval`, `.generation`, `.requests` со статусом, `.fallback` с фиксированной причиной. Лог содержит ID подбора, версии, статус и длительности фаз, без полного запроса и модельного текста. Индивидуальные request ID не используются как метки метрик. Публичное раскрытие actuator-метрик не добавлено.

Docker-тесты покрывают Java-регрессию, неизвестные/отрицательные/конфликтующие свойства, источники другого товара, просрочку, draft, версии, публикацию/откат/отзыв, явный выбор, смену комнаты, UI и контракты. Шлюз проверяется с подставным транспортом Ollama; реальный inference на сервере и нагрузочные p95 этим не измеряются.

Для промышленного пилота остаются независимые экспертные 50+ сценариев, согласованные пороги качества, реальные проверенные SKU и источники, оценка полноты технологий, испытания на целевом оборудовании и сравнение baseline/dense/hybrid. Малый исследовательский корпус и тестовые фикстуры не являются экспертным допуском.

## Исследовательский поиск по PDF без привязки к SKU

Дополнительно реализован отдельный opt-in путь для предоставленного пользователем корпуса. Он не является опубликованной базой технических свойств. По умолчанию выключен и не участвует в проверке совместимости, ранжировании SKU или применении выбора.

Офлайн-сборка без сети:

```bash
python3 scripts/rag/build_reference_index.py \
  --manifest data/rag/documents-v1/manifest.json \
  --manifest data/rag/coverage-v1/manifest.json \
  --output reports/material-recommendations/2026-11-07/reference-index \
  --allow-draft
```

Требуется `pdftotext` (Poppler). Скрипт проверяет SHA-256 каждого PDF, извлекает все страницы с сохранением границ страниц и строк, создаёт фрагменты до 1200 символов и сохраняет неизменяемый каталог по хешу корпуса. Отмечает пустые страницы и пропущенные нескачанные документы. OCR и интерпретация таблиц как числовых норм не выполняются. Ссылка на запрошенный файл не подменяет ссылку на фактически полученный документ; при неизвестном происхождении URL остаётся `null`, версия и замечания из реестра сохраняются.

Для отдельного исследовательского стенда укажите `RAG_REFERENCE_SEARCH_ENABLED=true` и `RAG_REFERENCE_INDEX=<абсолютный путь к каталогу-хешу>`. При работе в Docker этот каталог должен быть смонтирован только для чтения. Версии и checksum корпуса, количество документов и фрагментов проверяются Java на каждом запросе. Повреждённый индекс даёт `references.status=unavailable`, основной подбор остаётся доступен.

В запрос `/api/v1/material-recommendations` добавьте `referenceSearch: true`. В UI это отдельный, по умолчанию снятый флажок «Искать в справочных PDF». Ответ `references` содержит исследовательский `indexId`, фрагменты с ID источника, страницей, версией, хешем, статусами проверки/прав и отдельное модельное объяснение. Всегда `corpusMode=research_draft` и `usableForDecisions=false`; у справочных фрагментов нет `productId`.

При `explain=true` справочные фрагменты передаются через операцию шлюза `references/explain` в настоящую Ollama. Контекст ограничен шестью фрагментами, до двух на документ. Модель не получает разрешения выбирать товары, подтверждать SKU, назначать нормы или параметры проводки. Шлюз и Java проверяют закрытую схему и ссылки на извлечённые chunk ID. Произвольный текст всё равно остаётся `unverified_model_text`, а исходные PDF — черновиками. При отказе/таймауте модели сохраняются найденные фрагменты и `deterministic` fallback. Эта операция имеет отдельный лимит Ollama 60 секунд и Java 65 секунд; UI при совместном вызове двух объяснений ожидает до 110 секунд. Это технические лимиты, не обещание p95 на целевом оборудовании.

Исследовательский opt-in не означает проверки прав хранения, актуальности или инженерного допуска. Для рабочих рекомендаций по конкретным SKU по-прежнему необходимы проверенная привязка, утверждённые источники и отдельная публикация `KnowledgeBundle`.

`scripts/rag/live_probe.py` запускает финальную проверку на явно указанном пользователем хосте Ollama: временная сеть, отдельная тестовая MongoDB в tmpfs, актуальный JAR и актуальный LLM-шлюз. Используются синтетический краткоживущий внутренний токен и существующая установленная модель. Проверка вызывает настоящий публичный Java endpoint, проверяет модельные chunk ID и запрет применения черновых PDF к учебным товарам. Скрипт не подключается к рабочей БД и удаляет только созданные им контейнеры/сеть; отчёт сравнивает ID и время запуска рабочих контейнеров до/после. Тестовый JAR и индекс во временном каталоге остаются для воспроизводимости; это не переключение рабочего релиза.

Локальный inference: `live_probe.py --local --directory <staging-каталог в рабочем проекте>` использует существующий `repaircalc-ollama-1`, образы `repaircalc-backend:local`, `repaircalc-estimator:room-plan-v1` и `mongo:7.0`. При локальном запуске тест задаёт `RAG_REFERENCE_TIMEOUT_SECONDS=600`, чтобы CPU-inference не ограничивался GPU-лимитом по умолчанию. Параметр поддержан Java и LLM-шлюзом; диапазон 1–1800 секунд, default 60. Общие `LLM_REQUEST_TIMEOUT_SECONDS` и `OLLAMA_TIMEOUT_SECONDS` также должны быть достаточны. Для браузера на таком стенде можно задать `VITE_REFERENCE_TIMEOUT_MS=650000`; по умолчанию ожидание остаётся 110000 мс. Увеличение таймаута не считается прохождением нагрузочной приёмки.

## Удалённый сервер: контекст и пересборка индекса

CD и `scripts/release.py` задают контекст **32768 токенов** (`env/rag.env.example`). Это полный бюджет входа и генерации. Локальный Compose сохраняет 16384, CPU-проба использовала 8192. Явно заданные GitHub Environment variables имеют приоритет. Readiness проверяет фактический `context_length` через Ollama `/api/ps` и блокирует деплой при меньшем контексте.

При каждом AI-деплое Ansible запускает на целевом сервере отдельный одноразовый контейнер `rag-index` из LLM-образа того же commit. Образ содержит исходные PDF, реестры, Poppler и сборщик. Готовый индекс с рабочей машины не передаётся. Контейнер работает без сети, БД, Ollama и секретов, проверяет SHA-256 документов и заново извлекает все страницы. Даже при неизменившемся хеше выполняется повторное извлечение и сравнение результата. Сборка завершается до резервного копирования БД и перезапуска приложений; ошибка PDF или индекса останавливает деплой, сохраняя предыдущий релиз.

Каждый релиз по умолчанию имеет собственный `docker/reference-index/`: неизменяемые версии по SHA-256 и атомарную ссылку `current`. Backend получает индекс только для чтения. Переключение `current` выполняется после успешной полной сборки. Старые версии сохраняются для отката. Приватный результат шага записывается в `reference-index-build.json` релиза.

Настройки CD по умолчанию:

```text
OLLAMA_CONTEXT_LENGTH=32768
RAG_REFERENCE_SEARCH_ENABLED=true
RAG_REFERENCE_INDEX_HOST_PATH=./reference-index
RAG_REFERENCE_INDEX=/app/reference-index/current
RAG_REFERENCE_TIMEOUT_SECONDS=60
```

Справочный путь явно помечен `research_draft`, `usableForDecisions=false`, `productLinks=0`; сборка не подтверждает права, актуальность документов или свойства SKU. Локальный Compose по умолчанию не включает поиск: для ручной проверки задайте параметры из примера, выполните `docker compose ... --profile llm run --rm --no-deps rag-index`, затем запустите backend. Для CPU таймаут можно увеличить отдельно. После деплоя проверьте `POST /api/v1/material-recommendations` с `referenceSearch=true`, `explain=true`, статус и ссылки ответа.
