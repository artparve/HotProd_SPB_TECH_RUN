# Сборка и запуск frontend в Docker

Выполняйте шаги по порядку. Все команды запускаются **из корня проекта**, где находится `Makefile`. Они одинаковы для Windows, macOS и Linux.

Поднимается только frontend с nginx. Backend в Compose не включён: используйте деморежим или отдельно запущенный API.

## Шаг 1. Проверьте инструменты

Нужны GNU Make, Node.js 22.12+ или 24 LTS, Docker Engine и Docker Compose v2. Docker должен работать в режиме **Linux containers**.

```bash
make --version
node --version
docker version
docker compose version
```

В выводе `docker version` должны быть разделы **Client** и **Server**. Если Server недоступен, сначала запустите Docker Desktop или Docker Engine. Продолжать сборку до этого не нужно.

Если GNU Make установлен под именем `gmake` или `mingw32-make`, заменяйте `make` этим именем во всех следующих командах. `nmake` не подходит. Варианты установки инструментов описаны в [FRONTEND.md](FRONTEND.md#windows-macos-и-linux).

## Шаг 2. Создайте локальные настройки

```bash
make init-config
```

Команда создаёт два файла:

1. `env/.env` — переменные окружения.
2. `docker/docker-compose.override.yml` — локальная публикация порта и доступ контейнера к хосту.

Если файлы уже существуют, Make пропускает их создание и **не меняет содержимое**. Отдельных скриптов инициализации нет — вся операция описана в Makefile.

`make init` тоже существует, но дополнительно устанавливает npm-зависимости на компьютер. Для запуска через Docker это не требуется: зависимости устанавливаются внутри сборочного контейнера.

## Шаг 3. Заполните env/.env

Откройте **`env/.env`** в редакторе. Не редактируйте вместо него `.env.example` и не создавайте env-файлы в других папках.

Для первого запуска **без backend** укажите:

```dotenv
VITE_DATA_MODE=demo
VITE_API_BASE_URL=/api/v1
API_UPSTREAM=http://127.0.0.1:8000
DOCKER_API_UPSTREAM=http://host.docker.internal:8000
FRONTEND_HOST=127.0.0.1
FRONTEND_PORT=8080
IMAGE_TAG=local
```

Назначение каждой переменной:

| Переменная | Что указать |
| --- | --- |
| `VITE_DATA_MODE` | `demo`, если backend нет. `api`, если нужно обращаться к реальному backend. При ошибке API автоматического перехода в demo нет. |
| `VITE_API_BASE_URL` | Оставьте **`/api/v1`**. Это путь браузерных запросов через nginx, не адрес backend. |
| `API_UPSTREAM` | Адрес backend для Vite при разработке **без Docker**. Для текущего Docker-запуска не используется; можно оставить `http://127.0.0.1:8000`. |
| `DOCKER_API_UPSTREAM` | Адрес backend, доступный **из контейнера nginx**. Для backend на этом же компьютере — `http://host.docker.internal:8000`. |
| `FRONTEND_HOST` | `127.0.0.1` — frontend доступен только на этом компьютере. Для доступа с других компьютеров укажите `0.0.0.0` и настройте firewall. |
| `FRONTEND_PORT` | Свободный порт хоста, например `8080`. Если занят, выберите другой, например `8081`. |
| `IMAGE_TAG` | Тег локального Docker-образа: например `local` или `0.1.0`. Это имя версии, а не команда публикации образа. |

Для **реального backend** измените `VITE_DATA_MODE` на `api` и укажите подходящий `DOCKER_API_UPSTREAM`:

```dotenv
VITE_DATA_MODE=api
DOCKER_API_UPSTREAM=http://host.docker.internal:8000
```

Если backend на другом сервере, вместо этого укажите его адрес, например:

```dotenv
DOCKER_API_UPSTREAM=http://192.168.1.50:8000
```

Адрес backend — схема, хост и порт, **без `/api/v1` и без завершающего `/`**. Не указывайте `http://127.0.0.1:8000` для backend на хосте: внутри контейнера это адрес самого nginx-контейнера.

Backend должен поддерживать [OpenAPI-контракт](openapi.yaml). Для размещения backend на хосте он должен слушать интерфейс, доступный контейнеру, а firewall — разрешать это соединение. Backend, доступный только через loopback хоста, может быть недоступен Docker. В локальном override уже настроено имя `host.docker.internal`.

Сохраните файл. Не задавайте эти же переменные отдельно в окружении терминала: значения окружения имеют приоритет над `env/.env`. В `VITE_*` нельзя записывать секреты — они попадут в браузерный JavaScript.

## Шаг 4. Проверьте локальный override

Откройте **`docker/docker-compose.override.yml`**. Для обычного запуска его содержимое должно включать:

```yaml
services:
  frontend:
    ports:
      - "${FRONTEND_HOST:-127.0.0.1}:${FRONTEND_PORT:-8080}:8080"
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

Внутренний порт контейнера — `8080`. Внешний порт меняйте через `FRONTEND_PORT` в `env/.env`, а не через Dockerfile.

Файлы `env/.env` и настоящий `docker/docker-compose.override.yml` игнорируются Git. Не добавляйте их принудительно в коммит.

## Шаг 5. Проверьте конфигурацию

```bash
make config
```

При успехе команда завершится без ошибок. Она ещё не запускает контейнер и не проверяет доступность backend. Если появилась ошибка YAML, переменных или портов, исправьте её до следующего шага.

## Шаг 6. Соберите образ и запустите контейнер

```bash
make up
```

Эта **одна команда выполняет и сборку, и запуск**:

1. Скачивает базовые образы Node и nginx, если их ещё нет.
2. Устанавливает frontend-зависимости внутри Docker через `npm ci`.
3. Проверяет TypeScript и собирает frontend с `VITE_*` из `env/.env`.
4. Создаёт образ `repaircalc-frontend:<IMAGE_TAG>`.
5. Запускает nginx в фоне и ожидает успешный healthcheck.

Для первой сборки нужен доступ к Docker Hub и npm registry. На хосте не нужно выполнять `npm install`, `make build` или `make release`.

Если требуется **только собрать образ, не запуская контейнер**, используйте `make image` вместо `make up`. Для обычного запуска отдельно выполнять обе команды не нужно.

## Шаг 7. Проверьте контейнер и страницу

```bash
make ps
```

Сервис `frontend` должен иметь состояние `Up` / `running` и здоровье `healthy`.

При настройках из шага 3 откройте в браузере:

- **`http://127.0.0.1:8080`** — приложение.
- **`http://127.0.0.1:8080/healthz`** — ответ `ok`.

Если изменили `FRONTEND_PORT`, замените `8080` в адресах. Если включили доступ из сети через `FRONTEND_HOST=0.0.0.0`, с другого компьютера открывайте `http://<IP-сервера>:<FRONTEND_PORT>`, а не `http://0.0.0.0:...`.

Healthcheck подтверждает только работу nginx. Он не подтверждает работоспособность backend или корректность реальных товарных данных.

## Шаг 8. Проверьте выбранный режим

- В режиме **`demo`** откройте общий калькулятор, нажмите «Подобрать материалы», затем «Рассчитать смету». Должна появиться учебная смета без обращения к backend.
- В режиме **`api`** выполните те же действия. Должны выполняться запросы к `/api/v1/...` на адресе frontend, которые nginx передаст backend. При ошибке проверьте `DOCKER_API_UPSTREAM`, сетевую доступность и соответствие backend контракту.

Если приложение не открывается или запросы завершаются ошибкой, посмотрите логи:

```bash
make logs
```

`Ctrl+C` прекращает просмотр логов, но не останавливает контейнер. Ошибка `502` обычно означает недоступность backend для nginx; ошибка `503` может означать неготовность API. Ошибка схемы ответа означает, что backend вернул JSON, не соответствующий контракту.

## Обновление настроек и остановка

После изменения `env/.env` или кода повторите:

```bash
make config
make up
```

`make up` пересоберёт изменившиеся части и обновит контейнер. Для `VITE_*` пересборка обязательна: обычный restart не меняет уже собранный JavaScript.

Для остановки и удаления контейнера проекта:

```bash
make down
```

Образ не удаляется. Локальные настройки и сохранённые в браузере сметы остаются.

> Эта инструкция поднимает frontend по HTTP. Перед открытым размещением в интернете отдельно настройте HTTPS/reverse proxy, firewall и согласованную защиту backend. Не считайте `FRONTEND_HOST=0.0.0.0` полноценной production-конфигурацией.
