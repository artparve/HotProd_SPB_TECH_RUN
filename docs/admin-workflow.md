# Версия товара → классификация → проверка → публикация → расчёт

Продолжение административного CRUD от 30.10.2026. Админка доступна по `/admin`; все операции ниже используют сессию, CSRF и `If-Match` UUID сохранённой версии. Витрина должна работать в `VITE_DATA_MODE=api`, чтобы показать опубликованный товар. [Отчёт приёмки](../reports/admin-workflow/2026-10-30/README.md).

## Задания и worker

V6 хранит неизменяемый вход задания, UUID товара и конкретной версии. `POST /api/v1/admin/products/{id}/classifications` быстро возвращает 202; повторный запуск, пока версия queued/running, возвращает то же задание. `GET` того же пути возвращает последние 50 заданий, включая устаревшие. Ошибка или классификация не меняет карточку и не создаёт публичный товар. Результат после изменения карточки остаётся в истории, но API проверки не принимает его для новой версии.

`python -m repaircalc_classifier.worker` использует существующий `classify` и проверки цитат/закрытой таксономии. Вызов Ollama проходит вне транзакции. Очередь: `FOR UPDATE SKIP LOCKED`; аренда 90 секунд, heartbeat каждые 20 секунд, запись только с действующим lease token. После падения процесс возьмёт просроченное задание. Максимум три попытки, задержки 15/30 секунд; потеря последней аренды завершает задание `worker_lost`. Другая ошибка даёт `classification_failed`, сохраняя вход. Завершённые задания защищены триггером от изменения/удаления. Новый явный запуск после failed создаёт новое задание.

Worker не имеет HTTP-порта. Подключение — стандартные libpq `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`; отдельный `CLASSIFIER_DB_DSN` необязателен. Секреты не выводятся в лог. `OLLAMA_URL`, `OLLAMA_MODEL`, `OLLAMA_NUM_THREADS` задают исполнение, timeout 600 секунд. Compose включает `classifier-worker` в профиль `llm`, с restart, лимитами памяти/CPU и read-only FS. Запуск после настройки существующего `env/.env`:

```bash
docker compose --env-file env/.env -f docker/docker-compose.yml -f docker/docker-compose.override.yml --profile llm up -d --build classifier-worker ollama
```

Модель должна быть предварительно установлена согласно [deploy.md](deploy.md). Worker сам не скачивает её. Если Ollama недоступен, задание выполнит ограниченные повторные попытки; после исправления нажмите запуск снова. Нет гарантии единственного вызова модели: восстановление может повторить inference, но только владелец действующей аренды запишет итог.

## Решения человека и соответствие таксономий

UI показывает предложения, состояния свойств, причины review и цитаты с путями полей. Для каждого предложения нужны accept/reject/correct и непустое основание. Исправленная метка должна входить в закрытый словарь; у свойств — yes/no/unknown/conflict. API не меняет модельный ответ: V7 сохраняет решения, утверждённые значения, автора, job/version и результат сопоставления отдельными неизменяемыми строками. Решения не заполняют норму, цену и свойства карточки автоматически. Эти значения подтверждаются в форме с источником. Для опубликованной версии повторная проверка запрещена — сначала сохраните новую версию.

Python использует `repair-product-taxonomy-v2`, Java — `work-taxonomy-v1`. `classifier-java-reviewed-v1` — ограниченное сопоставление после проверки человеком, а не автоматическое равенство словарей:

| Утверждённая метка Python | Дополнительные условия | Код Java |
| --- | --- | --- |
| `floor` | `surface_locations=floor`, `kind=covering` | `floor` |
| `paint` | `surface_locations=wall`, `kind=paint` | `paint` |
| `wallpaper` | `surface_locations=wall`, `kind=wallpaper` | `wallpaper` |
| `electrical` | `kind=socket` или `cable` | `electrical` |

Основание: определения Python явно шире четырёх Java-кодов в V3. Например, наружная окраска/лак не означают окраску стен; грунтование не переводится автоматически в `paint`. Остальные метки, поверхности, основания и свойства остаются в утверждённом результате; без поддерживаемого соответствия публикация блокируется. `moisture_resistant` не превращается в `wet`, `frost_resistant` — в `unheated`. Java-копия словаря в resources должна побайтно совпадать с Python taxonomy; изменение версии требует пересмотра mapping и тестов. Это ограничивает первую вертикаль четырьмя проверенными случаями и не обеспечивает публикацию всех Python-категорий.

## Готовность и атомарная публикация

`GET .../readiness` вычисляет блокировки, UUID актуальной проверки и текущего базового release. Обязательны подтверждённые категория, цена/RUB/дата, вид, единицы; источник карточки; проверка успешной классификации текущей версии; Java work mapping; совместимая активная пара каталога/правил. Администратор явно выбирает профиль действующего набора. Проверяются фасовка, kind/unit, норма и единица расхода, геометрия/раппорт для обоев; `RuleSetValidator` проверяет форму и назначения. Неизвестные булевы сохраняются как null.

`POST .../publish` повторно проверяет всё под общим с CLI advisory lock и блокировкой строки карточки. Он копирует действующий каталог, все другие товары, raw source aliases и work mappings; для выбранного товара сохраняет UUID и прежний `cod_good`, заменяет revision и raw запись его внешней идентичности. Новый набор правил сохраняет профили, источники, тарифы и назначения остальных товаров, меняя только назначение проверенного товара и точную ссылку на новый fingerprint/version каталога. `RuleSetValidator` проверяет весь новый набор против всех товаров.

Каталог, правила, активация, состояние карточки и аудит фиксируются одной транзакцией. Ошибка в любой точке откатывает всё. Старые опубликованные снимки и их правила остаются неизменяемыми и доступны запросам, уже выбравшим старый release. Повторный publish одной версии возвращает первоначальную публикацию и не реактивирует старый снимок. Новые независимые публикации сериализованы общим advisory lock. CLI сохраняет прежний отдельный жизненный цикл импорта; его использование по-прежнему требует согласованного импорта правил.

Текущий движок принимает только `dataClass=test`. Админка публикует только в такую базу и использует существующие учебные профили; создание производственных норм, редактор правил, публикация без готовности к расчёту, архивирование, массовый импорт, очередь внимания и серверные рекомендации остаются следующим этапом. Утверждение меток не доказывает соответствие товара реальному нормативу.

## Проверки

Java: `AdminWorkflowIT`, `AdminProductApiIT`, `AdminProductPersistenceIT`, `CatalogImportIT`, `RuleSetImportIT` плюс unit/API-тесты Maven. Frontend: `make check`. Классификатор: unittest; очередь проверяется только с явным `CLASSIFIER_QUEUE_TESTS=1` на одноразовой мигрированной БД, используя `PG*`. Тесты очереди не вызывают LLM. Реальный inference и браузерный результат описаны отдельно в отчёте, чтобы не смешивать их с тестовыми ответами.
