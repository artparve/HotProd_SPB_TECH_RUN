# Техническая спецификация: админка каталога и классификация

Дата: 30.10.2026. Статус: предложение к реализации, не описание готового API. Основание — требования к дополнительному блоку админки и текущие исходники репозитория. Цель: сотрудник создаёт и проверяет товар, публикует его и получает возможность найти и рассчитать его в пользовательском интерфейсе; затем выполняет пакетную обработку.

## 1. Существующая система и границы

- Java/Spring Boot и PostgreSQL: `GET /api/v1/products` читает активный неизменяемый `catalog_release`; `POST /api/v1/product/{id}/calc` рассчитывает товар по совместимым опубликованным каталогу и набору правил. Миграции V2–V4 защищают опубликованные данные; импорт подготовленного каталога и правил сейчас выполняется CLI. Детали: [backend/README.md](../backend/README.md), [миграции](../backend/src/main/resources/db/migration/).
- Существующая публичная схема `Product` требует, среди прочего, положительную цену, категорию, поддерживаемый `kind`, единицы и источник; она не представляет произвольный неполный черновик. Frontend валидирует ответы Zod и в API-режиме получает массив из `/api/v1/products`: [контракт](openapi.yaml), [клиент](../frontend/src/services/api.ts), [типы](../frontend/src/domain/types.ts). Демо-режим использует фикстуры и не доказывает интеграцию с каталогом.
- Java контроллеры сейчас реализуют только список товаров и расчёт товара. Пути `/recommendations` и общей сметы в OpenAPI не означают готовую реализацию. Для реальных рекомендаций нужна отдельная серверная разработка; демо-подбор не является приёмкой этой функции.
- [Классификатор](../backend/classification/README.md) — отдельный Python-модуль, не API и не очередь. Он принимает строгий нормализованный `Product`, проверяет Pydantic-схему и точные цитаты; семантическая правильность требует человека. Его таксономия шире Java `work-taxonomy-v1`, автоматического соответствия нет. Версия и хеши, указанные модулем, не фиксируют digest весов модели.
- Java остаётся источником расчётных формул, денежных сумм и округления. Предложение LLM никогда не изменяет правила расчёта и не становится утверждённым автоматически. Эта спецификация не подтверждает запуск текущего стенда или готовность описанных ниже изменений.

## 2. Роли, сценарии и объём

Роли: аутентифицированный **администратор каталога** и анонимный **пользователь** публичных сценариев. Сервер проверяет полномочия каждого административного запроса. Администратор создаёт и изменяет карточку, классифицирует сохранённую версию, проверяет вывод, публикует и архивирует, ищет требующие внимания карточки, импортирует файл и просматривает журнал.

Первая поставка — ручная вертикаль: создание → классификация → решение по меткам → публикация нового снимка → товар в публичной выдаче → расчёт для поддерживаемого вида. Пакет и реальные рекомендации — последующие этапы, но входят в итоговый объём. Каталожная доступность, пригодность для рекомендаций и расчёта — независимые результаты проверки, а не три состояния публикации.

## 3. Данные и версия товара

Предлагается отдельная административная область таблиц через новую Flyway-миграцию, без изменения опубликованных ревизий V2–V4:

| Сущность | Содержание и ограничения |
|---|---|
| `admin_product` | UUID, `(source_namespace, external_id)` с уникальным ограничением, текущая версия, состояние `draft/review/published/archived`, время и автор; внешняя идентичность не перепривязывается к другому UUID. |
| `admin_product_version` | Неизменяемая версия с номером и снимком полей; создаётся при каждом изменении. Импорт существующих товаров в админку должен сохранять исходный UUID и идентичность. |
| `classification_job` | UUID, product/version, состояние, попытка, время, ошибка безопасного вида, параметры версии модели и worker lease. |
| `classification_result` | Неизменяемый входной снимок и хеш, полный доступный ответ/метаданные, валидированный результат отдельно, диагностика и версии taxonomy/prompt/model, digest модели при доступности. Не выдавать невалидный ответ за результат. |
| `label_decision` | Ось, значение/состояние, решение и комментарий, автор/время, ссылка на предложение и версию товара; ручная метка может не иметь предложения. История не перезаписывается. |
| `import_batch`, `import_item` | Снимок входа, построчный статус и ошибки, связь с карточкой и заданием; обработка независима для каждого элемента. |
| `audit_event` | Идентификатор запроса, актор, время, действие, объект, версии до/после и безопасные детали. Запись события и изменение состояния — в одной транзакции. |

Карточка содержит артикул, название, описание, категорию, список характеристик `{name,value,unit}`, цену как десятичную строку, валюту и дату актуальности, `unit`, `saleUnit`, `packageSize`, расход и его единицу, область и ограничения, источники, комментарий, а также поля `kind`, `wet`, `highLoad`, `unheated`, размеры рулона и раппорт там, где необходимы текущему `Product`. Для каждого важного значения хранить состояние `unset` (не заполнено), `unknown` (явно неизвестно), `confirmed` (значение проверено), с источником и автором подтверждения; не трактовать `unknown` как `false`. Состояние `confirmed` без значения недопустимо. Черновик допускает неполноту; название и внешняя идентичность обязательны для сохранения. Цена/фасовка/расход при наличии должны быть положительными, раппорт — неотрицательным, валюта и единицы проверяются по поддерживаемому справочнику. Дубликат идентичности — 409 с ссылкой на существующую карточку.

Изменение создаёт новую версию и помечает предыдущие результаты классификации устаревшими. До повторного подтверждения нельзя переносить их в новую публикацию без явного решения администратора; текущий опубликованный снимок при этом остаётся неизменным. Решения привязаны к версии, а не к изменяемой карточке. Для согласованности `published` означает, что именно указанная версия включена в активный release; если опубликованная карточка редактируется, рабочая версия становится `draft`, а активная версия продолжает обслуживать пользователей до следующей публикации.

## 4. Классификация и ручная проверка

Java API создаёт устойчивое задание по сохранённому `productVersionId`; Python worker забирает его из PostgreSQL и вызывает существующий `classify` через библиотечный интерфейс. Адаптер строит только поддерживаемый вход `source`, `source_id`, `cod_good`, `name`, `description`, `marketing_description`, `categories` и `attributes` из снимка. Порядок характеристик и пути evidence сохраняются; не передавать служебные комментарии и секреты. Зафиксировать точный вход и его SHA-256 до вызова. Текущий модуль при ошибке не гарантирует сохранение полного сырого ответа: расширить обёртку для безопасной записи доступного raw/parse error и метаданных, не обещая получить отсутствующие данные при обрыве.

Состояния задания: `queued → running → completed | needs_review | failed`. `completed` означает успешную техническую проверку; все предложения всё равно требуют решения человека. `needs_review` отражает флаг модели/конфликты, `failed` — в том числе нарушение схемы или цитаты. Интерфейс опрашивает статус, не блокирует вкладку и не показывает выдуманный процент inference. Ограничение worker по умолчанию — одна одновременная модельная задача, настраиваемое окружением. Для перезапуска использовать транзакционное получение задания и lease с истечением; после сбоя возвращать просроченные `running` в очередь, сохранять попытки, защищать запись результата от завершившегося поздно старого worker. Повтор создаёт новую попытку, не стирая старую. Для одного товара и версии одновременный повторный запуск возвращает действующее задание; явный повтор после завершения создаёт новое.

Показывать `scope`, все виды работ, места, основания, состояния свойств `yes/no/unknown/conflict`, цитату с точным полем и исходным текстом, причины проверки, времена и версии. Несовпадение текущей версии и версии задания явно отмечать как устаревший результат; операции применения по нему отклонять 409. Подтверждение, отклонение, замена допустимой меткой и ручное добавление сохраняют отдельные решения, автора, время и комментарий. Массовое подтверждение применяется только к выбранным валидным предложениям актуального задания, атомарно с проверкой версии; спорные `conflict` и `unknown` требуют отдельного решения. Сохранить также `out_of_scope` и отсутствие подходящей работы; отсутствие предложения не означает отрицание свойства. Цитата доказывает наличие текста, но не корректность вывода.

Таксономии не объединять по совпадению названий. Добавить версионированную таблицу явных соответствий classifier taxonomy → Java work taxonomy с ревизией и ручным подтверждением; неподдержанная или неоднозначная метка остаётся в админке и не попадает в старые назначения. Новые виды работ требуют отдельно расширить Java taxonomy, данные, фильтрацию и расчётные правила. `wet/highLoad/unheated` разрешается заполнять только из явно проверенного соответствия свойств с сохранением `null` для неизвестного.

## 5. Публикация и вычисляемая готовность

Перед публикацией API возвращает список причин по каждому сценарию:

1. **Каталог:** поля, необходимые существующей публичной `Product`-схеме и ограничениями БД, включая подтверждённые цену, категорию, `kind`, единицы и источник. Неполный черновик остаётся в админке. Для показа товаров без этих полей потребуется отдельно изменить публичный контракт и UI; не записывать фиктивные значения.
2. **Рекомендации:** подтверждённые соответствующие назначения и известные либо явно неизвестные свойства. Если подходящей работы нет, товар можно оставить только каталожным; не включать его в подборы по предположениям.
3. **Расчёт:** все поля и входные параметры конкретной стратегии, подтверждённые цена и фасовка, а также подходящий опубликованный профиль правил. Например, для краски/грунта/клея необходима согласованная с профилем норма, для обоев — размеры рулона и раппорт; не требовать норму для розеток и кабеля. Проверять средствами Java, а не отдельной копией формул во frontend. Возвращать машиночитаемые причины и текст для пользователя.

Публикация — серверная операция создания **полного нового** catalog release на основе активного снимка с заменой выбранной проверенной версии; нельзя опубликовать только одну запись и потерять остальные. Под тем же механизмом сериализации, что и существующий импорт, проверить исходный release и version карточки, построить назначения, проверить ограничения, записать fingerprint/manifest и атомарно активировать release. При конфликте или ошибке прежний release остаётся активным. Для архивирования аналогично создаётся снимок без товара для новых подборов; прежние снимки и UUID сохраняются.

Правила привязаны к release: до активации нового каталога подготовить и проверить совместимый новый rule set, включая профили для существующих товаров и нового товара, если расчёт допустим. Активация пары должна быть согласованной для читателей; если это невозможно без изменения текущей модели публикации, сначала реализовать такую согласованную операцию. Не допускать регрессии расчётов старых товаров из-за нового release без правил. Для каталог-only товара сохранить совместимые правила остальных товаров и вернуть понятную недоступность его расчёта. Нельзя предполагать, что одной заполненной нормы товара достаточно: текущий Java-код использует профиль и проверяет согласованность.

Существующие ответы содержат версии каталога и правил; устойчивое хранение пользовательских смет здесь не подтверждено. Для сохранённых смет реализовать неизменяемый снимок строк/цены/версии товара, catalog и rules или ссылки на сохранённые immutable snapshots; архивирование и переиздание не должны менять старую смету. В API-режиме обновить публичный UI: непригодный товар виден в допустимой выдаче, расчёт отключён и показана причина. Это потребует расширения OpenAPI/Zod и Java ответа, так как текущий Product не содержит полной информации о готовности.

## 6. Предлагаемый административный REST-контракт

Пути ниже — проект, добавить в [OpenAPI](openapi.yaml) при реализации; префикс `/api/v1/admin` позволяет использовать существующий `/api/` proxy. Везде JSON UTF-8; даты RFC 3339 UTC, деньги — десятичные строки, UUID — строки. `X-Request-ID` возвращается во всех ответах. Секреты и stack trace клиенту не выдаются.

| Метод и путь | Действие / успешный ответ |
|---|---|
| `GET /products?q=&category=&workType=&status=&classificationStatus=&readiness=&sort=&page=&size=` | Страница `{items,page,size,total}`; сортировка по created/updated с UUID как tie-breaker. |
| `POST /products` | Создать черновик, 201 + `Location`, карточка с `version`. |
| `GET /products/{id}` | Поля рабочей и опубликованной версий, готовность, утверждённые метки, последнее задание и ссылки на историю. |
| `PUT /products/{id}` | Полный снимок данных, обязательный `If-Match` версии; новая версия и ETag. |
| `GET /products/{id}/history` | Постраничная история версий, решений и событий. |
| `POST /products/{id}/classification-jobs` | По текущей сохранённой версии, 202 + `Location` задания. |
| `GET /classification-jobs/{id}` | Статус, версия входа, времена, диагностика и валидированные предложения. |
| `POST /classification-jobs/{id}/retry` | Новая попытка, 202; прежняя сохраняется. |
| `POST /products/{id}/label-decisions` | Список решений, `If-Match`, ссылки на актуальное задание; атомарное применение. |
| `GET /products/{id}/readiness` | `{catalog,recommendations,calculation}`, каждый `{ready,reasons:[{code,message,field}]}`. |
| `POST /products/{id}/publish`, `POST /products/{id}/archive` | `If-Match`, проверка и атомарная публикация; ответ содержит версии release/rules и статус. |
| `POST /imports/preview` | Загрузка и валидация файла без изменения каталога; возвращает batch ID, сводку и ошибки. |
| `POST /imports/{id}/commit` | Явно подтвердить импорт допустимых строк; 202 и прогресс. |
| `POST /imports/{id}/classification-jobs` | Поставить выбранные импортированные версии в очередь. |
| `GET /imports/{id}`, `GET /imports/{id}/report` | Прогресс и JSON-отчёт по строкам и заданиям; повтор ошибок через отдельные задания. |

Все пути в таблице относительно `/api/v1/admin`. Предлагаемая ошибка: `{code,message,requestId,details:[{field,code,message}]}`. `400` — неверный JSON, `401` — нет сессии, `403` — нет роли, `404` — объект отсутствует, `409` — дубликат/устаревшая версия или результат/конкурирующая публикация, `412` — несовпадение `If-Match`, `422` — ошибки полей или готовности, `428` — отсутствует обязательный `If-Match`, `503` — недоступны БД/очередь/каталог. Уточнить единообразие 409/412 в OpenAPI: 412 исключительно для HTTP-предусловия, 409 для бизнес-конфликта. Ошибка модели отражается в задании, а не 500 от уже принятого запроса. Для создания задания и commit импорта поддержать `Idempotency-Key`, хранить ключ с хешем запроса и результатом; повтор с другим телом — 409.

## 7. Импорт

MVP-формат — UTF-8 JSON-массив объектов карточки с теми же названиями полей, что у admin API; пример и JSON Schema добавить вместе с реализацией. Установить конфигурируемый предел размера и числа строк; отклонять неизвестные поля и некорректные типы. Preview не меняет карточки: показывает все обнаруженные поля, число строк, новые/существующие идентификаторы, ошибки полей и дубли внутри файла и БД. Строки с одинаковой идентичностью внутри файла считать ошибочными, не выбирать победителя автоматически. Для существующих карточек показывать различия и требовать явный выбор обновления; применить с проверкой версии, чтобы не затереть изменения после preview. Для новых создавать черновики. Каждый элемент обрабатывается отдельной транзакцией и имеет собственный результат; ошибка не отменяет остальные. Повтор commit идемпотентен. Очередь и отчёт переживают рестарт; отчёт содержит номер строки, идентичность, действие, UUID/версию, ошибки, job ID и итог проверки без секретов.

## 8. Интерфейс и доступ

Добавить административные маршруты в существующее frontend-приложение и отдельный типизированный клиент/Zod-схемы; не использовать демо-адаптер для административных операций. Экраны: вход; список с поиском, фильтрами, сортировкой и пагинацией; очередь внимания; карточка с полями, источниками, статусами и историей; сравнение предложения и решения с цитатами; preview/прогресс/отчёт импорта. В карточке отдельно показать рабочую и опубликованную версии, сохранение, причины готовности и устаревшие результаты. При 412 показать конфликт и предложить перечитать карточку, не перезаписывая чужие правки. Ошибки, загрузка, пустая выдача, отключённая модель и недоступная сеть имеют понятные состояния. После публикации обновлять данные пользовательской выдачи, не выдавая локальный черновик за опубликованный товар.

Для стенда предлагается один именованный администратор с серверной сессией: пароль хранится только как стойкий хеш в конфигурации/секретах окружения, cookie `HttpOnly`, `Secure` при HTTPS и `SameSite`, истечение сессии, серверная проверка роли и CSRF-токен для изменяющих запросов. Нужны вход, выход, ограничение попыток и отсутствие пароля/токена в журнале. На публичном стенде использовать HTTPS и ограничение сетевого доступа к админке. Подключить маршруты к текущей конфигурации proxy и Compose, передавая внутренние адреса через окружение; не раскрывать браузеру адрес Ollama. Проверить изоляцию административных и публичных маршрутов.

## 9. Проверка и приёмка

Автоматизированные проверки включают:

- миграции PostgreSQL, неизменяемость snapshots, уникальность идентичности, конкурирующие правки и публикации, атомарное переключение каталога и правил, rollback, сохранение старой сметы;
- API: роли, CSRF, все статусы ошибок, `If-Match`, idempotency, фильтры, аудит, устаревший результат, повтор после сбоя;
- классификатор: строгий вход, точные пути и цитаты, ошибки схемы, `unknown/conflict/out_of_scope`, несколько работ, неверные и устаревшие предложения; worker с подменой транспорта, lease и перезапуском;
- импорт: preview без записи, дубли, неполные и ошибочные строки, обновление с конфликтом, частичный успех, повтор и восстановление после рестарта;
- frontend: Zod-контракты, формы, очередь, решения и причины недоступности, конфликт версии и обработка ошибок;
- сквозной тест реального браузера в API-режиме: новый товар → сохранение → модельное задание → проверка нескольких меток → публикация → появление в выдаче → Java-расчёт, независимый эталон денег/упаковки и идентификаторы версий. Отдельно проверить товар без нормы, отклонённую метку, отключённую модель, архив и перезапуск.

Для подтверждения рекомендаций требуется реализованный серверный endpoint и проверка появления товара в каждой подтверждённой работе и отсутствия в отклонённых. Если он ещё не реализован, отметить этот критерий как не пройденный. Тесты с заглушкой модели и реальный вызов Ollama фиксировать раздельно; качество классификации оценивать на независимой размеченной выборке, а не по успешности JSON/evidence. Сохранить отчёт с версиями исходников, данными, командами, результатами и ограничениями. Приёмка завершена, когда все требуемые сценарии из исходного задания, включая пакет и перезапуск, подтверждены; первая вертикаль сама по себе — промежуточная веха.

## 10. Порядок реализации

1. Согласовать расширение публичного контракта, таблицы, соответствия таксономий и транзакцию catalog/rules; миграции и тесты совместимости.
2. Серверная авторизация, аудит, версии и CRUD; экран списка и карточки.
3. Устойчивая очередь, адаптер существующего классификатора, решения и история; контролируемый worker.
4. Готовность, согласованная публикация снимков и правил, публичный UI и сквозной расчёт.
5. Реальные серверные рекомендации по утверждённым меткам; расширение поддерживаемых видов работ отдельно от классификации.
6. Пакетный preview/import, очередь и отчёт; интеграционные, браузерные и модельные проверки.
