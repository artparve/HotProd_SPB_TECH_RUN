# План реализации: извлечение параметров комнаты из плана

Дата: 30 октября 2026 года.

Статус: реализация начата. При подготовке плана распознавание не проверялось;
30 октября добавлены контракт черновика, серверный маршрут и утилита эксперимента.
Первый реальный вызов установленной Docker Gemma выполнен; результаты и ограничения:
[отчёт реализации](../reports/room-plan/2026-10-30/README.md).
Добавлен интерфейс загрузки/вставки изображения, проверки и применения размеров.
Проверки через браузер Codex: [отчёт UI](../reports/room-plan/2026-10-30/ui/README.md).
Выделение фрагмента внутри сайта и итоговая проверка качества ещё впереди.

Пункт хакатона: **3.4. Опционально — «вау»-демо: извлечение параметров комнаты из плана помещения (CV) → автозаполнение калькулятора.**

## 1. Цель и пользовательский сценарий

Пользователь загружает план → Gemma извлекает размеры → пользователь проверяет их на изображении → калькулятор заполняется и рассчитывает материалы.

Для первого прототипа использовать существующую `gemma4:12b` через Ollama без обучения отдельной CV-модели. Модель поддерживает изображения, а Ollama позволяет передавать их через `images` и задавать JSON Schema ответа. Качество чтения планов и совместимость установленной версии необходимо проверить экспериментально.

Источники:

- [Gemma 4 12B в Ollama](https://ollama.com/library/gemma4:12b).
- [Передача изображений в Ollama](https://docs.ollama.com/capabilities/vision).
- [Структурированные ответы Ollama](https://docs.ollama.com/capabilities/structured-outputs).

## 2. Границы MVP

Начать с одной прямоугольной комнаты. Пользователь загружает PNG/JPEG или выделяет комнату на плане квартиры. На изображении должны быть читаемые внутренние размеры.

| Параметр | Поведение |
| --- | --- |
| Длина и ширина | Извлекать подписанные размеры, переводить в метры |
| Название и назначение | Предлагать, если они явно указаны |
| Высота потолка | Извлекать только при наличии подписи, иначе запрашивать |
| Окна и двери | Вычислять площадь только при известных ширине и высоте |
| Площадь и периметр | Рассчитывать кодом по подтверждённым размерам |
| Работы, запас, слои, условия эксплуатации | Оставлять для выбора пользователя |

Ограничения:

- Без размеров или достоверного масштаба нельзя определять метры по изображению. Для MVP основной способ — чтение подписанных размеров; измерение по масштабу можно добавить отдельно.
- По одной площади нельзя однозначно восстановить длину и ширину.
- Текущий `Room` и геометрия рассчитаны на прямоугольник. Г-образные и другие сложные комнаты отмечать как неподдерживаемые, предлагая ручной ввод.
- Импорт всех комнат квартиры отложить до проверки основного сценария.
- Не подставлять неизвестные параметры молча из текущих значений формы, например высоту `2.7` м или площадь проёмов `3.5` м².

## 3. Этап 1 — эксперимент с Gemma

До разработки интерфейса проверить качество извлечения и время ответа.

1. Подготовить 10–15 планов: чёткие подписи, миллиметры, десятичные запятые, несколько комнат, нечитаемые размеры и отсутствие масштаба.
2. Вручную записать эталонные значения.
3. Отправлять изображение и инструкцию: извлекать только видимые сведения, неизвестное возвращать как `null`.
4. Проверить совместную работу передачи изображения и JSON Schema в установленной версии Ollama.
5. Измерить время ответа, ошибки чтения и случаи выдуманных размеров.

**Результат:** примеры запросов и ответов, таблица качества, замеры времени и решение, достаточно ли одного вызова Gemma.

Если мелкие подписи читаются плохо, сначала проверить выделение и увеличение комнаты. Отдельный OCR подключать по результатам эксперимента.

## 4. Этап 2 — контракт распознавания

Ответ модели представляет черновик, а не готовый объект `Room`.

Для каждого извлекаемого поля предусмотреть:

- значение и исходные единицы;
- прочитанную подпись, например `4200`;
- область изображения, где находится подпись;
- состояние: «найдено», «неизвестно» или «конфликт».

Дополнительно возвращать форму комнаты, предупреждения и список недостающих данных. Координаты задавать в согласованной системе, например нормализованными относительно переданного изображения. При выделении фрагмента сохранять преобразование координат к исходному плану.

Проверять структуру, допустимые значения, единицы и противоречия на сервере. Правильная структура JSON не гарантирует правильного распознавания: подписи и координаты остаются предложениями модели для проверки пользователем.

Зафиксировать версию схемы и промпта для воспроизводимости.

**Результат:** схема черновика, правила валидации и примеры успешного, неполного и конфликтного ответа.

## 5. Этап 3 — серверное распознавание

Для MVP расширить существующий Python estimator отдельным модулем распознавания, переиспользовав подключение к Ollama.

Предлагаемый новый маршрут: `POST /api/v1/plans/extract`. Маршрут является частью плана, его ещё требуется реализовать.

Последовательность обработки:

1. Проверить формат, размер файла и число пикселей.
2. Подготовить изображение, сохранив читаемость подписей.
3. Передать изображение Gemma с JSON Schema и версионированным промптом.
4. Проверить структуру, единицы, диапазоны и противоречия.
5. Вернуть черновик и предупреждения.

Для первой версии достаточно одного запроса с тайм-аутом и ограничением параллельных распознаваний. Если замеры покажут слишком долгое выполнение, добавить задания с опросом статуса.

Текст внутри изображения считать данными: он не должен менять инструкции модели или запускать инструменты.

**Результат:** работающий маршрут, обработка ошибок изображения и модели, тесты валидации и преобразования единиц.

## 6. Этап 4 — интерфейс и подтверждение

Основная точка входа — кнопка **«Заполнить по плану»** рядом с параметрами комнаты.

Сценарий:

1. Пользователь загружает изображение и при необходимости выделяет одну комнату.
2. Интерфейс показывает ожидание распознавания и позволяет обработать ошибку или повторить попытку.
3. После ответа отображаются изображение и таблица полей.
4. При выборе поля подсвечивается соответствующая подпись на плане.
5. Пользователь исправляет найденные размеры и вводит недостающие значения, включая высоту и необходимые параметры проёмов.
6. Кнопка **«Применить параметры»** переносит подтверждённые значения в выбранную комнату.
7. Существующий калькулятор рассчитывает материалы по подтверждённым параметрам.

Не применять результат к другой комнате и не перезаписывать изменения, сделанные пользователем во время ожидания. Перед применением выполнить существующую валидацию комнаты.

Gemma отвечает за извлечение. Формулы, округление и стоимость остаются в детерминированном коде и Java API.

## 8. Этап 5 — проверки и критерии готовности

Целевые критерии, которые ещё предстоит подтвердить:

- На отдельном проверочном наборе читаемых планов не менее 90% подписанных размеров извлекаются правильно после перевода единиц. Набор и правило сравнения зафиксировать до итоговой проверки; не использовать только примеры настройки промпта.
- На планах без размеров система возвращает неизвестные значения, а не придуманные числа.
- Ручная корректировка и повторная загрузка работают.
- Неподдерживаемая форма, конфликт единиц и нечитаемые подписи обрабатываются явно.
- Неизвестные параметры не заменяются скрытыми значениями по умолчанию.
- Расчёт после импорта совпадает с расчётом при ручном вводе тех же параметров.
- Время распознавания измерено на машине показа, интерфейс корректно обрабатывает ожидание и ошибку.

Проверки по компонентам:

- Frontend: `make check`, проверки подтверждения полей, неизвестных значений и применения к выбранной комнате.
- Estimator: `PYTHONPATH=backend/estimation python3 -m unittest discover -s backend/estimation/tests`, проверки контракта, единиц, ошибок и ответов модели через подменённый транспорт.
- Реальный сценарий: загрузить свежий план в браузере, дождаться ответа Gemma, подтвердить размеры и проверить итоговый расчёт.
- Java: выполнять проверки при изменении Java-кода или контрактов расчёта.

Отдельно сохранять результаты проверок без модели и результаты реального мультимодального запуска. В свидетельства включать входной пример, эталон, ответ, подтверждённые параметры, версию модели/промпта и время выполнения.

## 9. Подготовка демонстрации

Подготовить три примера:

1. Хороший план — успешное извлечение и автозаполнение.
2. План с недостающей высотой — явный запрос недостающего значения.
3. План без размеров и масштаба — объяснение, почему нужен ручной ввод.

Перед показом проверить сценарий на целевой машине и прогреть модель. Если нужен резервный записанный результат, явно обозначить его как запись предыдущего запуска.


## 10. Возможное развитие после MVP

- Выбор и импорт нескольких комнат с одного плана.
- OCR для мелких размерных подписей, если эксперимент подтвердит необходимость.
- Измерение по явно заданному масштабу с проверкой пользователем.
- Поддержка сложной геометрии после расширения модели комнаты и расчётных контрактов.
- Асинхронные задания, если длительность распознавания потребует этого.
