Приоритеты: **P1** — блокирует целевой сценарий или надёжную интеграцию; **P2** — необходимо для расширения и воспроизводимой эксплуатации; **P3** — документация/дополнительные возможности. Это приоритет работ, не утверждение об аварии на стенде.

## 2. Архитектурные расхождения

### A01 — PostgreSQL вместо MongoDB из исходной схемы · P1, решение архитектуры

**План:** в PNG явно указан Mongo и запись tags в него. **Факт:** PostgreSQL используется во всём persistence: `backend/pom.xml`, `application.yml`, миграции V1–V7, JPA repositories, `JdbcTemplate`, JSONB, advisory locks, очередь `FOR UPDATE SKIP LOCKED`, Compose `postgres`. MongoDB driver, модели коллекций и сервис Mongo в составе ветки отсутствуют.

**Почему это нужно закрыть:** исходная схема и фактическая архитектура расходятся. Однако PostgreSQL соответствует `PLAN.md`, Java-плану и принятому ADR-001. Поэтому автоматически объявлять эту БД ошибкой или менять её только в Compose нельзя.

**Исправление:** зафиксировать целевую БД. Если ориентиром остаётся исходный Mongo-драфт, выполнить отдельную миграцию: идентичности/ревизии/источники → коллекции; индексы и неизменяемость; согласованная публикация каталога/правил; транзакции, очередь/lease, миграция существующих данных, rollback, драйверы и тесты. Если сохраняется PostgreSQL — явно заменить исходную схему и записать причину отклонения.

**Закрыто, когда:** утверждён один ADR и схема; приложение, worker, индексы/транзакции, запуск и тесты соответствуют им; при миграции проверены перенос и восстановление данных. Эта запись сохраняет запрошенное пользователем расхождение, но не выдаёт наличие позднего ADR за отсутствующее решение.

### A02 — Java/Spring вместо Python/FastAPI из PLAN · P3, уже уточнённое решение

`PLAN.md` предлагает Python/FastAPI, фактически публичный бизнес-API написан на Java/Spring; Python estimator использует stdlib HTTP server, а не FastAPI. В начале Java-плана прямо сказано, что Java выбрана пользователем, ADR закрепляет выбор. Долг — синхронизировать старые архитектурные описания. Переписывать Java на Python только ради старого предложения не требуется.

### A03 — Python напрямую пишет в общую БД · P1, прямое нарушение границы Java-плана

BE-28 и раздел 10 запрещают Python запись в Java-БД и предлагают versioned batch/interface. `backend/classification/repaircalc_classifier/worker.py` сам меняет `repaircalc.admin_classification_job`; Compose передаёт worker те же `PGUSER/PGPASSWORD`, что используются для общей БД. Поведение связано с конкретными таблицами и SQL PostgreSQL.

Исправить через контролируемый API/адаптер выдачи задания и приёма результата либо оформить пересмотр границы с отдельной ролью БД и минимальными правами только на очередь. Сохранить lease fencing, идемпотентность, привязку результата к версии и отказ от устаревших результатов. Закрытие требует contract/integration tests, включая отсутствие прав менять каталог/цены/правила.

### A04 — Нет отдельного Room Classificator и цепочки `/design` · P1 для подбора, P2 для решения архитектуры

PNG: `POST /api/v1/design {room_type, room_size}` → room tags → товары → калькулятор. Факт: `RoomEditor.vue` задаёт условия вручную и начальными значениями по типу комнаты; клиент вызывает `/recommendations`, серверного обработчика нет. Распознавание плана — другая задача, оно не классифицирует пригодность материалов для помещения.

Реализовать серверный подбор и решить, нужен ли отдельный модельный классификатор комнаты. Для структурированного Room допустимы явные правила; отдельная LLM не является обязательным способом решения. Закрыть расхождение маршрутов через актуальный OpenAPI/схему, а не просто добавить пустой `/design`.

### A05 — RAG заменён объяснением результата калькулятора · P2

PNG предусматривает `tag → RAG → description`. В `estimation/service.py` LLM получает результат расчётного tool; поиска по корпусу норм/документов, retrieval-индекса и цитирования найденных документов нет. Evidence классификатора — цитаты входной карточки, это не RAG.

Если RAG остаётся целевой частью: определить проверенный корпус, версии документов, retrieval, ссылки на основания и поведение при отсутствии источника. Иначе снять RAG с актуальной схемы и явно ограничить объяснения фактами tool. Ни один вариант не должен делегировать модели деньги/упаковки.

### A06 — Автоматический матчинг превращён в обязательную ручную проверку каждой публикации · P1

PNG и требования предполагают автоматическое назначение меток новым товарам. Фактически создание карточки, запуск классификации, review и publish — разные действия. `AdminReviewService.validateDecisions()` требует решение и основание для каждого предложения; `AdminPublicationService.inspect()` блокирует публикацию без review текущей версии и выбора профиля.

Проверка человеком для неоднозначностей полезна, но сейчас не реализован путь автоматической обработки подтверждённых случаев. Нужны измеримая политика принятия, очередь сомнений и оценка доли автоматизации; не удалять проверки цены/норм ради автоматизации меток. Критерий: новый однозначный товар проходит согласованный путь без ручного проставления всех соответствий, спорный — остаётся на review.

## 6. Что изменилось относительно main и не является исходным требованием

Проверено именно `git diff --name-status main HEAD`, а не только diff от merge-base. Название merge-коммита не означает, что backend содержит весь актуальный main.

- В backend нет галереи интерьеров, `data/inspirations.ts`, доменных схем и соответствующих тестов. Это дополнительная функция main; её перенос нужно включить в план отдельно. Она не равна Room Classificator из PNG и не закрывает отсутствующий `/recommendations`.
- Нет ограниченного Markdown renderer и его тестов из main. Текущее отображение объяснений следует оценивать по своей реализации; отсутствие renderer само по себе не доказывает XSS.
- Нет общего Node env-loader, `secret.env.example`, CI/CD/Ansible и release Compose из main. Первое — расхождение конфигурации, CI — ещё и невыполненный BE-26.
- В backend добавлены Windows/IDE способы запуска и локальный dotenv Spring. Это полезное дополнение, но не закрытие серверного подбора, общей сметы и воспроизводимой приёмки.
- Распознавание плана через Python и административные workflow уже существуют. Их не следует записывать как отсутствующие только потому, что ранний Java-план исключал ML из отдельного этапа.

## 7. Что уже соответствует плану и не нужно переписывать без причины

- Java 21/Spring/Maven foundation; PostgreSQL/Flyway/JPA соответствуют уточнённому backend-плану и ADR.
- Каталог и rules имеют версии/проверки; источники и raw записи, multi-work mappings, неизменяемые снимки и согласование catalog/rules реализованы для подготовленных учебных данных.
- Материальный калькулятор использует BigDecimal, целые упаковки, остатки и формулы; есть стратегии покрытий/краски/грунта/клея/обоев/розеток/кабеля и явные отказы неполным данным.
- Product API и каталог — реальные контроллеры, а не заглушки в этом сравнении. Их качество исполнения текущими тестами здесь не подтверждалось.
- Есть административная авторизация/CSRF, версии/ETag, задания, review и атомарная публикация; есть Python lease/heartbeat/retry и проверка evidence.
- Локальные saved/cart/JSON соответствуют Java-плану. Заказ, оплата, аккаунты и межустройственное хранение не являются автоматически обязательным долгом. PLAN прямо допускает JSON корзины до появления контракта магазина.
- Ограниченный реалистичный тестовый каталог разрешён ответами организаторов. Само количество 12 SKU не является нарушением; долг — доказать новые товары, расширяемость и качество.
- Планы BE-21…23 допускают отложенный full import; это незавершённый backlog, а не доказательство ошибки уже согласованной MVP-поставки.
