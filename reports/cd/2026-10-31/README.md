## Причины отказов и исправление

Первый prod запуск остановился на защите от автоматического принятия старой PostgreSQL базы как MongoDB. Запуск prod-mongo конфликтовал со старым frontend на 8080. Само создание Environment не меняет порт, схему данных или совместимость MongoDB с ядром хоста.

MongoDB 8.0.34 не проходила проверку совместимости фактического ядра хоста. Проверена MongoDB 7.0: изолированный replica set, транзакция и CRUD более 91 секунды, затем реальные Java интеграционные тесты. В prod установлены:

```text
DEPLOY_FRONTEND_PORT=8081
MONGO_IMAGE_TAG=7.0@sha256:8bb4442761a63a8dda452744082cdac9644b429807eb977b42324a63cef59ca4
```

Данные перенесены отдельной операторской процедурой с блокировкой исходных writers. Старые строки сохранены в архивной коллекции; рабочие документы сохраняют IDs, историю и Decimal128. Для совместимости старых правил добавлены обязательные kits/priority и проверенные materialFamily. Исходные нормы и цены не заменялись.

## Закрытые свидетельства и откат

Все исходные данные, дампы, контрольные суммы, отчёты сравнения, результаты восстановления и исходный Caddy config находятся на сервере в `/opt/repaircalc/migration-20261031/final-20261031T171753Z`. Конфигурация удалённых PG-контейнеров сохранена там в `retired-postgres-inspect.json` с ограниченными правами. Секреты и дампы в Git не включены. CD дополнительно сохранил Mongo backup перед обновлением.

Откат после новых записей в Mongo требует отдельного решения о данных; сохранённые PG volumes соответствуют моменту миграции. Не переключать ingress обратно вслепую. Для восстановления старых контейнеров использовать сохранённый inspect и volumes; не публиковать приватный inspect/config.

Операторские скрипты этой папки относятся к этому конкретному переносу и содержат фиксированные пути и имена. Они не являются автоматическим универсальным deploy workflow. Успешный CD развёртывал уже опубликованный commit f4c7347; последующий коммит tooling/docs фиксирует выполненный перенос и не означает нового развёртывания приложения.
