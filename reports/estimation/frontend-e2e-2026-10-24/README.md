## Результат

**Четыре реальных браузерных сценария прошли полный цикл:** ввод полей формы → nginx → Python estimator → Gemma4 tool call → Java ProductCalc → PostgreSQL → второй вызов Gemma → смета и пояснение в интерфейсе.

На момент начала задачи estimation-сервис уже существовал, но frontend вызывал Java `/product/{id}/calc` напрямую. Для проверки полного цикла добавлено его подключение к карточке товара. Реальные inference запускались нажатием «Рассчитать упаковки» во встроенном браузере на `http://127.0.0.1:8080/product`; не подменялись curl-ответами или фикстурами модели.

Независимые эталоны:

- Краска: `37.5 × 0.12 × 3 × 1.12 = 15.12`; `ceil(15.12 / 5) = 4`; `4 × 2490 = 9960`.
- Плитка: `13.7 × 1.08 = 14.796`; `ceil(14.796 / 1.44) = 11`; `11 × 2160 = 23760`.
- Обои: полотно `ceil((2.6 + 0.10) / 0.32) × 0.32 = 2.88 м`; из рулона `floor(10.05 / 2.88) = 3` полотна; нужно `ceil(21.4 × 1.07 / 1.06) = 22`; `ceil(22 / 3) = 8`; `8 × 1890 = 15120`. Проёмы не вычитаются.
- Розетка: процентный запас не применяется; `9 × 349 = 3141`.

Все цены, карточки и нормы — подготовленные **тестовые** данные, не текущие цены магазина и не подтверждённые нормы производителя. Стоимость работ во всех четырёх расчётах `0.00`. Проверка подтверждает арифметику и передачу параметров, а не коммерческую достоверность исходников.

## Реализованное подключение

- В API-режиме карточка товара по умолчанию включает «Добавить пояснение ИИ» и вызывает `/api/v1/materials/estimate`. Снятие флажка явно выбирает прежний Java endpoint без модели; автоматического fallback нет.
- Новый envelope проверяется Zod, включая tool call, количество строк, режим и UUID выбранного товара. Изменение товара/параметров во время ожидания не позволяет показать устаревший ответ.
- Суммы берутся только из `estimate`. Непроверенное пояснение показывается отдельно как текст с именем модели и предупреждением; HTML модели не исполняется. При сбое только пояснения успешная смета сохраняется.
- Для `/api/v1/materials/` добавлены отдельные Vite/nginx proxy и переменные `ESTIMATION_UPSTREAM` / `DOCKER_ESTIMATION_UPSTREAM`. Два вызова модели на CPU требуют увеличенного ожидания: nginx 1250 с, браузер 1260 с. Другие API сохраняют прежние таймауты.
- HTTP-ошибки с корректным `ApiError` теперь показывают сообщение сервера. OpenAPI и инструкции запуска обновлены. Формулы Java и исходный алгоритм estimator не изменялись.

## Оставленный стенд

- Frontend: `http://127.0.0.1:8080`, контейнер `repaircalc-frontend-1`, API mode.
- Java: `http://127.0.0.1:8000`, `repaircalc-backend-check`.
- PostgreSQL: `repaircalc-postgres-check`, том `repaircalc-pgdata-check`.
- Estimator: `http://172.17.0.1:8010`, адрес Docker-интерфейса хоста; nginx обращается через `host.docker.internal:8010`. Процесс не опубликован на LAN.
- Ollama: `http://127.0.0.1:11434`, `gemma4:12b`; модель может автоматически выгрузиться после простоя и загрузиться на следующем запросе.

После сохранения доказательств тестовый аудит остановлен и оставлен штатный Python HTTP-сервис без записи дальнейших пользовательских запросов в отчёт. Для повторного запуска Python из корня проекта:

```bash
PYTHONPATH=backend/estimation python3 -m repaircalc_estimator serve --listen 172.17.0.1
```

Адрес `172.17.0.1` проверен на этом компьютере; на другом хосте нужно определить свой Docker gateway. В локальном `env/.env`: `VITE_DATA_MODE=api`, `DOCKER_API_UPSTREAM=http://repaircalc-backend-check:8000`, `ESTIMATION_UPSTREAM=http://172.17.0.1:8010`, `DOCKER_ESTIMATION_UPSTREAM=http://host.docker.internal:8010`. Пересборка: `make up DOCKER='docker --config /tmp/repaircalc-docker-config'`. Этот Compose по-прежнему управляет только frontend. PostgreSQL/Java настраиваются по [TEAM_SETUP](../../../backend/docs/TEAM_SETUP.md).

## Оставшиеся ограничения

Сквозное подключение относится к **расчёту одного товара**. Общая смета `/estimate`, подбор `/recommendations` и админка в этой задаче не реализовывались. Объяснения модели не являются источником сумм; в этих прогонах она иногда дублировала смету JSON-блоком и Markdown, которые UI показывает обычным текстом. Четыре успешных примера не доказывают общую достоверность свободных объяснений. Проверка выполнена на desktop; мобильный layout и полный цикл заказа не проверялись.
