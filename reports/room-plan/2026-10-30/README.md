# Начало реализации извлечения параметров комнаты — 30 октября 2026

Последующее продолжение: [реализованный UI и проверка мышью в Codex](ui/README.md).
Ниже сохранён отчёт первого серверного этапа до подключения интерфейса.

Реализован первый серверный срез плана. Это не завершённый пользовательский MVP:
интерфейс загрузки/выделения/подтверждения и перенос в выбранную комнату ещё не подключены.
Исходные изображения пользователя и существующие отчёты admin-workflow сохранены.
Изменения не закоммичены, исходный HEAD/ветка и SHA-256 файлов —
[source-snapshot.json](source-snapshot.json).

## Что работает

- `POST /api/v1/plans/extract` в Python estimator, запрос JSON `imageBase64`.
- PNG/JPEG/WebP по фактическому формату; проверка декодирования, размеров,
  анимации, пикселей; EXIF-ориентация, белый фон прозрачности, удаление метаданных.
- Один запрос Ollama с изображением, JSON Schema и версионированным промптом.
  Инструменты модели не передаются, ответы с tool calls отклоняются.
- Проверка структуры, состояний, исходных единиц, числовой подписи, bbox и границ;
  перевод мм/см/м в метры через Decimal. Неизвестное остаётся `null`.
- Для нескольких комнат и неподдерживаемой формы нормализованные длина/ширина
  не предлагаются для переноса. Нулевые проёмы не назначаются автоматически.
- Общая блокировка с `materials/estimate`: второй запрос получает `503 model_busy`.
- Маршрут в nginx/Vite и OpenAPI; зависимости и ресурсы включены в Docker-образ.
- Утилита `backend/scripts/room_plan_experiment.py` сохраняет запрос, исходный
  ответ модели даже при отказе валидации, подготовленное изображение, digest,
  версии, контрольные суммы и время. Вариант `--docker-container` не требует
  опубликованного порта Ollama и не скачивает модель.

Контракт: [OpenAPI](../../../docs/openapi.yaml),
[схемы API](../../../docs/room-plan-api.json).
Запуск описан в [README estimator](../../../backend/estimation/README.md).

## Реальные вызовы установленной Docker Gemma

Контейнер `repaircalc-ollama-1`, модель `gemma4:12b`, ID `6114515d63c1`,
Ollama `0.40.2`, Q4_K_M, CPU. `/api/show` сообщает capability `vision`.
Подтверждено совместное использование `images` и `format` с JSON Schema.
Полный digest и настройки в summary каждого запуска.

### Кухня

Вход: пользовательский `Кухня · 18,3 м².png`, 1920 × 1358.
Внутренние подписи при визуальном чтении: 5,32 × 3,32 м; внешние 5,62 × 3,62 м.
Эталон не выводился из имени файла или ответа модели.

- Результат: `length=5.32`, `width=3.32`, `height=null`, `shape=rectangle`.
- Внешние размеры не перепутаны с внутренними. Высота и размеры проёмов неизвестны.
- Полное время утилиты 231,519 с; обращение к модели 231,052 с.
- Время загрузки модели по Ollama около 23 с; это один запуск, не распределение задержек.
- Ошибка: модель перечислила 4 окна, визуально видны 3. Вместе с дверью получились
  5 проёмов вместо 4. Их размеры остались неизвестными, площадь не вычислялась.
- Координаты некоторых подписей неточны, в частности название смещено вниз.
  Структурная проверка bbox не доказывает попадание в подпись.

Артефакты: [summary](kitchen-v1/summary.json), [запрос](kitchen-v1/request.json),
[сырой ответ](kitchen-v1/raw-response.json), [черновик](kitchen-v1/result.json),
[переданное изображение](kitchen-v1/prepared.png).

### Детская без явных единиц — неудачный ответ модели, отказ сервера

Вход: `635164-plan-komnaty-chertezh-5.jpg`, 1330 × 1500. Ожидание: не восстанавливать
общие размеры по мебели/цепочкам и не предполагать мм без явной подписи единиц.

- Время утилиты: 198,210 с, Ollama: около 197,736 с.
- Модель нарушила инструкцию: сама указала в предупреждении, что приняла мм
  по типовым размерам мебели. Кроме того, приняла подпись `700` за ширину двери.
- Для length/width вернула `state=conflict`, `value=null`, но `unit=mm`;
  это нарушает контракт неизвестного/конфликтного поля.
- Сервер отклонил весь ответ: `502 invalid_plan_draft`,
  `Unknown/conflicting field contains a usable value: length`.
  Утилита завершилась с кодом 1, `result.json` не создан; исходный ответ сохранён.
- Это **не** успешное извлечение неизвестных значений. Проверка схемы и состояний
  остановила именно этот некорректный черновик. Она не доказывает, что другой ответ
  с угаданными единицами и формально корректной структурой будет распознан автоматически.

Артефакты: [summary](children-no-units-v1/summary.json),
[запрос](children-no-units-v1/request.json),
[сырой ответ](children-no-units-v1/raw-response.json),

## Границы выводов и следующие шаги

[development-cases.json](development-cases.json) содержит 7 просмотренных исходных
изображений с SHA-256 и ожидаемым поведением: кухня, отсутствие единиц, футы/дюймы,
две комнаты и уступы стен. Это набор разработки, не независимая проверка точности.
Пользователь подтвердил: пока поддерживать только мм, см и метры.

Результат одного хорошего плана не подтверждает критерий 90%. Нужны ещё 10–15
планов с вручную подтверждёнными внутренними размерами, включая отсутствие размеров,
нечитаемые подписи и конфликт единиц; отдельная часть должна оставаться проверочной.
Ошибки проёмов и bbox требуют проверки человеком даже при правильных длине/ширине.
Негативный запуск показал, что одного промпта недостаточно для запрета угадывания
единиц. Перед интерфейсом стоит расширить контракт отдельным подтверждением подписи
единиц и её координат (в том числе общей подписи плана), проверить этот вариант
экспериментально; даже такое подтверждение остаётся предложением модели для человека.

Следующий этап: интерфейс выбора одной комнаты, подсветка подписей, явный ввод
недостающих высоты/площади проёмов и подтверждение; защита от применения к другой
или изменённой комнате. Затем сверка ручного ввода и импорта на детерминированном
расчёте. При задержке около четырёх минут следует оценить задания с опросом статуса;
пока маршрут синхронный, timeout Ollama по умолчанию 600 с, nginx — 650 с.
