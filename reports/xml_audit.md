## Качество и риски расчётов

- В **5 114 товарах** повторяется одно и то же имя param; у **3 983** оно имеет более одного разных сочетания value/unit. Нельзя строить словарь свойств простым «последнее значение побеждает»: нужно хранить исходные значения и отмечать конфликт/множественность (часть повторов может быть допустимой).
- Имена свойств имеют пробелы на конце и варианты регистра: `Длина`/`Длина `, `Толщина`/`Толщина `, `Назначение`/`Назначение ` и др.
- Единицы требуют нормализации: `м2`, `кв.м`, `кв.м./уп.`; `г/кв.м`, `г/кв.м.`, `гр/м2`; `м`/`м.`; `шт`/`шт.`. Нельзя смешивать площадь упаковки с площадью освещения, расход материала с расходом газа, транспортный `weight` с массой содержимого.
- Числа бывают `0,13`, `0.9`, диапазоны `50-70`, `1,3-4,5`; расход зависит от слоёв, основания, толщины. Недостающая норма должна оставаться явно неизвестной или брать проверенное правило с пометкой источника.
- Встречается конфликт описания с param: `offer id=3634790`, лак TURY ПФ-231 0,9л: description содержит расход **80–120 г/м²**, а param — **50–70 г/м²**. Кроме того, фасовка указана в литрах, расход в граммах — без плотности конверсия некорректна.
- Хороший пример для калькулятора: PLITONIT PLITOMAX 25кг (`offer id=15465716`), `Вес=25 кг`, `Расход=1,3–4,5 кг/м2`, `Толщина слоя=1–10 мм`. Но выбор точки диапазона должен быть обусловлен технологией/условиями, а не случайным средним.
- Пример контекстной рекомендации: PARADE W1 2,5л, `id=9425527`: акриловая, для потолков, матовая, влагостойкость «нет», помещение «с умеренной влажностью» — полезный отрицательный пример для влажного санузла.
- `description` содержит HTML `<br>` и часто короткий перечень свойств; необходимо чистить HTML, сохраняя сырые данные.
- Цены и `available=true` — состояние поставленного снимка, не проверка реальных остатков магазина.

## Сопоставление с products_final.json

Сделана только структурная сверка ключей, глубокий анализ JSON отдельный:

- JSON содержит 88 790 записей, 88 746 уникальных `cod_good`.
- Хвост XML URL после последнего `/catalog/.../` = JSON `cod_good`: точное совпадение у **56 207 XML товаров** (**91,53%**). XML-only — **5 199**, JSON-only уникальных cod_good — **32 539**.
- Сравнение XML URL без домена с JSON `url_key`: **54 621** совпадение, меньше, чем по cod_good (категорийный slug может различаться).
- XML `offer/@id` НЕ равен JSON `id`: **0 совпадений** среди идентификаторов. Пример XML id 17074358 ведёт на cod_good 1000002278. Не соединять по числовому id и не использовать неуникальный артикул.
- Сначала join по нормализованному `cod_good`, дубликаты JSON проверить отдельно. Совпадение ключа не гарантирует совпадение цены/свойств: политику источников выбрать явно.

## Полезность для хакатона и рекомендуемые следующие шаги

1. XML подходит как источник иерархии категорий, цен, изображений, ссылок и особенно **единиц характеристик**, которых может не хватать в JSON. Сохранить snapshot date и происхождение каждого поля.
2. Построить нормализованный каталог с ключом cod_good, отдельными raw/normalized attributes, поддержкой ranges и конфликтов. Не терять единицы и не объединять разные физические величины.
3. Отобрать вертикали для демо: краска, обои, плитка/клей, напольные покрытия; на них измерить покрытие обязательными расчётными полями.
4. Расчёт геометрии, расхода, запаса и округления упаковок делать детерминированным кодом; LLM/ML использовать для категории работ и ограничений помещения, не для арифметики и выдумывания расхода.
5. Создать небольшой ручной эталон SKU с достоверной фасовкой/расходом/условиями и отрицательными примерами; конфликты и нехватку данных выделять отдельно. Каталог не содержит тарифов ремонтных работ — их источник нужен отдельно.

Потоковый разбор исходного XML выполнен полностью; исходные файлы не изменялись. Применимых AGENTS.md по пути рабочей папки не обнаружено. Подробные машинные сводки: /tmp/spb_xml_stats.txt, /tmp/spb_xml_detail.json, /tmp/spb_xml_join.json.

## Уточнение неоднозначностей объединения

Все 61 406 cod_good из хвостов XML URL уникальны. В JSON **44 повторяющихся ключа**, каждый представлен дважды; **36 из них присутствуют в XML**. Поэтому raw join даст **56 243 строки**, но только **56 207 уникальных товаров**. У 16 из 36 совпавших дублей различаются цены, у 13 — имена. На стороне JSON не совпали **32 547 записей / 32 539 уникальных cod_good**, на стороне XML — **5 199**. Покрытие XML — **91.53%**, JSON по уникальным cod_good — **63.33%**. Нужна явная политика дублей и конфликтов, а не произвольный выбор первой записи.
